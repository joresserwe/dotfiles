# Codex 공통 기본값

이 규칙은 모든 Codex 세션·프로젝트의 현재 에이전트와 위임된 자식 작업에 적용한다. 사용자의 범위를 보존하고, 기존의 무관한 변경은 건드리지 않는다.

## 공통 규칙·스킬 — Claude 동기화

- Claude와 Codex 양쪽에 적용되는 규칙·스킬을 추가·수정·삭제하면 같은 작업에서 양쪽에 반영한다. 동기화를 후속 작업으로 남기지 않는다.
- 공통 스킬 원본은 dotfiles의 `skills/<name>/SKILL.md`에 둔다. `claude/skills/<name>`와 `codex/skills/<name>`는 모두 `../../skills/<name>`를 가리키는 상대 디렉터리 심볼릭 링크로 유지하고, 별도 복사본 대신 공통 원본을 수정한다.
- 공통 기본 규칙을 바꾸면 `claude/CLAUDE.md`에도 같은 의미로 반영한다. 상대 파일을 먼저 읽고 공통 지침의 충돌을 함께 해소한다. Codex 전용 도구·플러그인·권한·모델 설정은 분리한다.
- 이 작업에는 공통 `shared-skills` 스킬을 적용한다. 양쪽 저장소·전역 스킬 링크를 검증하고 완료하지 못한 동기화는 보고한다. 다운로드된 플러그인과 `skills/synced/`는 공통 원본에 포함하지 않는다.

## 토큰과 탐색

- 검색은 우선 `rg`로 하고, 관련 파일만 필요한 만큼 읽는다.
- 출력과 설명은 작업에 필요한 범위로 제한한다. 위임 지시와 최종 보고는 앞선 대화를 보지 않은 사람이 그것만 읽어도 이해되게 쓰고, 작업 중에 만든 약어·내부 명칭은 풀어 쓴다.
- 이미 성공한 검증은 새 증거가 없으면 반복하지 않는다.
- 작은 작업에 계획·리뷰 자식을 추가하지 않는다. 필요한 경우 기존 에이전트를 재사용하고, 중복되는 full-history fork를 피한다.

## 검증 배치

- 각 파일·패치·코드 작성 직후에 테스트·린트·빌드를 반복 실행하지 않는다.
- 의미 있는 기능·수정 묶음 또는 작업 마무리 시점에 관련 변경과 필요한 검증을 모아 최소 범위로 한 번 수행한다.
- 실패사항을 모아서 수정하고 실패·영향 범위만 재검증한다. 변경이 없으면 성공한 검사를 반복하지 않는다.
- 사용자가 명시했거나 다음 구현을 막는 오류 원인을 확인해야 하는 경우에만 좁은 중간 검증을 허용한다. 테스트를 아예 생략하는 규칙은 아니며, 완료 전에 필요한 검증은 유지한다.

## 작업 지속

- 요청 범위 안의 다음 단계는 제안만 하고 멈추지 말고 수행한다. 의도가 불분명하면 되돌릴 수 있는 합리적인 가정을 세우고, 그 가정을 보고에 밝힌 뒤 계속한다.
- 멈추고 묻는 경우는 범위가 크게 달라질 때, 실제로 막혔을 때, 사용자만 내릴 수 있는 결정일 때, 되돌릴 수 없거나 파괴적인 작업 직전뿐이다.
- 마치기 전에 요청의 각 항목이 충족됐는지 확인한다.

## 모델 라우팅

- 기본 모델은 `gpt-6.2-astra`의 `high`다. Astra(입력 별칭 `astro`)가 문제 정의·분석·계획·조사·설계·중요 판단과 맥락 의존적이거나 복잡한 구현·검증을 직접 수행하고 최종 결과를 책임진다.
- `gpt-5.6-luna`의 `xhigh`는 변경 위치·방법·기대 결과가 이미 확정된 단순·기계적인 코드·설정·스크립트·테스트 수정과 그 좁은 검증에만 사용한다. 위임·재설명·검토 비용보다 절감이 있을 때만 선택하고, 바로 끝나는 사소한 수정 때문에 자식을 강제 생성하지 않는다. 불확실성을 발견하면 임의로 범위를 넓히지 말고 근거와 함께 부모에게 반환한다.
- `gpt-5.6-sol`의 `high`는 질문·대상·기대 산출물이 명확한 독립 읽기 전용 분석·조사에 한해 위임한다. 문제 정의·분석 방향·개선 우선순위는 Astra가 책임지며, Sol은 근거·한계·불확실성을 반환하고 자동으로 Luna에 구현을 넘기지 않는다.
- `Terra`는 자동 라우팅에서 제외하며 사용자가 명시적으로 요청한 경우에만 사용한다. `gpt-5.6-terra` 프로필은 유지한다.
- 이 지침은 위 조건을 만족하고 위임 이점이 있는 좁은 하위 작업의 위임을 요청한다. 핵심 분석은 Astra가 직접 수행한다. 모델과 추론 수준은 실제 배정 기준으로 명시하고, 지정 시 `fork_turns=none` 또는 충분한 최소 컨텍스트를 사용하며 불필요한 full-history fork를 피한다. 실제 라우팅이 불가능하면 문구만으로 전환했다고 주장하지 말고 구체적인 수동 실행 명령을 제시한다.
- 글로 모델을 지시한다고 실제 부모 세션의 모델이 바뀌지는 않으며, 실제 라우팅과 권한은 설정과 모델 배정을 기준으로 확인한다.

## Gotchas — 실제로 틀렸던 것과 바로잡은 규칙

실제 작업에서 검토자가 되돌린 사례다. 사례가 새로 생기면 같은 형식(무엇이 틀렸나 → 규칙)으로 여기에 더한다.

- **설계가 요청보다 커진다.** 일별 누적 표 하나면 되는 일에 DB 함수·전용 계정·영수증 표·작업자 풀을 넣었고, "저장할 때 값 한 쌍을 기록"에 입력 출처 추적과 확정 단계를 넣었다. → 목표를 충족하는 가장 작은 설계를 낸다. 지시에 없는 장치는 본 설계에 넣지 않고 "추가 제안"으로 따로 적는다.
- **지시 문구를 글자 그대로 따라 수정 대상이 아닌 기존 동작까지 바꾼다.** "정확히 일치할 때만"이라는 문구를 따라, 대소문자·공백을 무시하던 기존 선택 규칙을 조였다. → 수정 대상 밖의 기존 동작은 그대로 둔다. 지시 문구와 기존 동작이 충돌하면 기존 동작을 지키고 충돌을 보고한다.
- **주변에 없는 장치를 새로 들이거나, 이미 있는 것을 다시 만든다.** 이웃 표에 없는 트리거·외래 키·boolean·CHECK를 썼고, 다른 화면에 이미 있는 입력 행을 새로 구현해 모양이 달라졌고, 이미 있는 권한 판정을 새 SQL로 베껴 원본과 어긋났다. → 같은 일을 하는 기존 코드·표·화면을 먼저 찾아 그 방식을 그대로 쓴다. 베끼지 말고 호출·재사용한다.
- **지어낸 표본으로 검증한다.** 조회문을 직접 만든 표본 행으로만 확인했고, 실제 행에서는 단위 표기와 선택지 코드 때문에 분류가 틀렸다. → 설계 전에 실제 데이터의 모양을 읽기 전용으로 본다. 검증은 실제 행으로 한다.
- **테스트가 고치려는 동작을 실행하지 않는다.** 가짜 저장소와 빈 대역 함수 위에서만 통과해, 실제 SQL과 이력 전달은 한 번도 돌지 않았다. → 테스트는 수정 전 코드에서 실패하고 수정 후 통과해야 한다. 시험 대상 자체를 대역으로 바꾸지 않는다.
- **한 요청만 본다.** 기능이 쓰인 그 턴만 확인해, 다음 턴에 전달되는 이전 답변이 빈 값이 되는 것과 수정 뒤 지난 기록이 숨는 것을 놓쳤다. → 상태가 남는 기능은 다음 요청, 다시 열기, 수정, 비활성화 뒤의 동작까지 따라가 확인한다.
- **기술 작업에 동작 규칙 변경을 섞는다.** 저장 방식을 바꾸는 작업에 한도 합산 규칙 변경을 함께 제안했다(구현하지 않고 결정 사항으로 올린 것은 옳았다). → 동작 규칙을 바꾸는 일은 구현하지 않고 결정 사항으로 올린다.
- **막힌 것을 하나씩 보고해 여러 번 멈춘다.** 번호 충돌, 문서의 측정 수치, 파일의 개인 경로를 각각 따로 보고하며 세 번 멈췄다(지적 자체는 모두 옳았다). → 한 단계에서 찾은 막힘은 모아서 한 번에 보고하고, 막히지 않은 부분은 끝까지 진행한다.
- **같은 문제에 변형을 계속 만든다.** → 두 번 시도해 측정으로 나아지지 않으면 세 번째를 만들지 말고 결과와 함께 "그대로 둠"을 보고한다.
- **적용 뒤 반영 절차를 코드에서 확인하지 않고 적었다.** 화면 문구(DB 메시지)를 바꾸는 묶음의 안내서에 "다시 로그인"만 적었는데, 그 문구는 서버 캐시에 최대 24시간 남는다. → 데이터 변경 안내서에는 그 데이터를 읽는 코드의 캐시·적재 시점을 확인해, 필요한 새로고침 호출이나 재시작을 적는다.
- **"다른 것은 영향 없다"를 한 경로로만 증명했다.** 역할-메뉴 행을 추가하면서 메뉴 트리만 확인하고, 같은 조회를 쓰는 다른 기능(채팅의 안내 범위 등)을 확인하지 않았다. → 권한·역할 데이터를 바꾸면 그 조회를 쓰는 소비자를 전부 찾아 각각 영향을 적는다.
- **바꾼 것을 쓰는 테스트를 찾아 돌리지 않았다.** 저장소 인터페이스에 조회를 추가하면서 그 인터페이스를 대역(mock·녹화 JDBC)으로 쓰는 테스트를 돌리지 않아 19건이 깨진 채 반영됐고, 도구가 내는 사실 수를 바꾸면서 그 번호를 기대하는 픽스처 생산 테스트를 돌리지 않았다. 한 커밋은 테스트 컴파일도 실패했다. → 인터페이스·메서드·결과 필드를 바꾸면 그것을 참조하는 테스트를 검색해 전부 돌린다. 커밋마다 테스트 컴파일을 확인한다.
- **화면 표기를 바꾸면서, 그 표기를 저장된 데이터와 비교하는 코드를 확인하지 않았다.** 표기 대소문자 변경 뒤 예전에 저장된 조건이 다른 조건으로 취급됐다. → 표시 문구를 바꾸기 전에 그 문구를 비교에 쓰는 코드를 검색하고, 저장된 데이터와의 비교는 식별자로 하도록 먼저 고친다.
- **실패한 비교를 느슨하게 만들어 통과시켰다.** 공유 기대 파일을 생성기로 다시 만들지 않고 따로 나눈 뒤, 키를 버리고 값만 비교하도록 테스트를 바꿨다. → 기대 파일은 생성기로 함께 다시 만든다. 기존 비교를 느슨하게 하지 않으며, 예전 파일을 남겨야 하면 이유를 보고서에 적는다.
- **반영할 상태가 아닌 상태의 테스트 결과를 보고했다.** 보류 패치를 붙인 채 돌린 통과 건수를 반영 대상의 통과로 적었고, 반영할 커밋 그대로는 한 번도 돌리지 않았다. → 보류한 것을 뗀 뒤, 반영할 커밋 그대로 대상 테스트(바꾼 클래스를 쓰는 테스트 포함)를 돌리고 그 결과만 보고한다.
- **동작을 바꾸는 줄을 실패하는 테스트 없이 넣었다.** → 커밋 안의 동작 변경마다, 그것을 되돌리면 실패하는 단언이 하나씩 있어야 한다.
- **로컬에만 있는 데이터에 기대어 확인 절차를 썼다.** 화면 확인을 안내하면서, 그 화면에 들어가는 권한 행이 로컬에서 손으로 넣은 것뿐이라는 점을 확인하지 않았다. → 안내서에 적는 확인마다 그 전제(권한·설정·데이터)의 출처가 기본 설치나 전달물인지 확인한다. 아니면 전달물에 넣거나, "안 되면 무엇을 보고할지"를 안내서에 적는다.
- **"기존과 같은 방식"이라고 보고했지만 절반만 같았다.** 시각 표시 함수는 재사용하면서 저장 시간대를 UTC로 고정해, 서버 시간대가 다른 환경에서는 9시간 어긋나게 만들었다. 같은 코드의 다른 곳은 요청에 실려 오는 서버 시간대로 읽고 있었다. → DB의 시간대 없는 시각은 그 프로젝트가 이미 쓰는 출처(서명된 서버 시간대)로만 해석한다. UTC·시스템 기본값 고정은 쓰지 않는다. "같은 방식"이라고 쓸 때는 비교한 파일과 줄 번호를 함께 적는다.
- **권한 부여 SQL이 다른 사용자를 막을 수 있다.** 역할 행이 0건이면 모든 로그인 사용자에게 열리는 API에 역할 행 하나를 더하는 SQL을 썼다. 대상 서버에서 그 API가 0건이면 기존 사용자가 막히는데, verify는 그것을 OK로 셌다. 같은 묶음의 다른 SQL에는 보호 조건이 있었다. → 역할 부여 SQL은 대상의 역할 행이 0건(전체 허용)이면 넣지 않고, verify는 그 경우를 따로 표시한다. 같은 전달물 안의 SQL끼리 보호 조건이 같은지 맞춰 본다.
- **확인 절차에 확인할 방법이 없다.** 메뉴로 갈 수 없는 화면을 "주소로 직접 열어 확인"하라고 쓰면서 주소와 시험 계정 조건을 적지 않았다. 관리자 계정으로는 SQL이 적용되지 않아도 화면 확인이 모두 통과한다. → 안내서의 화면 확인에는 페이지 주소와 시험 계정의 역할 조건(없어야 할 역할 포함)을 적는다.
- **전달 안내서가 전달물에 없는 파일을 가리킨다.** 개발서버로 나가는 SQL 묶음의 README가 근거·참고로 내부 작업 보고서 경로를 적었다. → 전달 README는 받는 쪽이 가진 파일만 가리킨다. 확인 절차와 제한 사항은 README 안에 다 적는다.
- **권한을 하나만 주고 화면이 동작한다고 결론낸다.** 화면이 호출하는 API 여러 개 중 요청받은 하나에만 역할을 부여했고, 같은 화면의 다른 API(검색)가 막혀 있다는 사실은 보고서 본문에만 적었다. → 권한 변경은 대상 화면이 실제로 호출하는 API 전부를 대상 역할로 대조한다. 빠진 것은 같은 전달물에 넣거나, 최종 보고 첫 줄에 "이것만으로는 화면이 동작하지 않음"이라고 쓴다.
- **"개발 소스"를 전달 태그가 아닌 커밋에서 읽는다.** 권한 점검이 개발서버 상태를 전달 태그보다 2커밋 앞선 작업 가지에서 읽고 "양쪽에서 수정됨"이라고 썼다. 개발서버에 있는 것은 태그까지다. → 개발서버 기준 주장은 `git show <전달 태그>:<경로>`로만 읽고, 읽은 커밋을 보고서에 적는다. 아직 적용되지 않은 증분은 "증분에 포함"이라고 따로 쓴다.
- **시험 데이터가 만든 건수를 제품 결함 건수로 보고한다.** "담당자가 열 수 없는 ToDo 93건" 중 담당자 계정은 전부 시드·시험 계정이었고, 17건은 현재 서버 규칙으로는 생길 수 없는 배정이었다. → 건수를 보고할 때는 실제 업무 계정과 시험 계정을 나누고, 현재 규칙으로 생길 수 없는 행은 "데이터 잔재"로 따로 센다. 제품 결함은 "역할을 제대로 준 서버에서도 생기는가"로 판정한다.
- **조사 중에 바뀐 상태를 다시 읽지 않는다.** 조사 도중 적용된 변경으로 이미 해소된 9쌍을 누락으로 셌다. → 긴 조사는 최종 수치를 보고 직전에 한 번 더 조회하고, 조회 시각을 적는다.
- **자기가 만든 퇴행을 다음 커밋에서 고치면서 테스트를 남기지 않는다.** 대소문자 무시 비교를 넣은 뒤 정확 일치 우선으로 고쳤는데, 그 동작이 없을 때 실패하는 테스트가 없었다. 처음 고친 테스트는 입력을 대문자로 바꾸는데 원래 값이 이미 대문자일 수 있어 아무것도 시험하지 않았다. → 동작을 바꾸는 커밋에는 그 동작이 없으면 실패하는 테스트를 같은 커밋에 둔다. 테스트 입력 변환이 실제로 값을 바꾸는지 단언한다.
- **계약 schema가 있는 데이터를 투영 단계에서 schema 밖 값으로 덮는다.** 계약 원본은 `NOT_SUPPORTED`인데 투영 코드가 매 턴 enum에 없는 값으로 바꿨다. 같은 사실이 두 곳에 반대로 남았다. → 계약 데이터가 틀렸으면 원본·schema·사본을 계약 순서대로 고친다. 범위 밖이라 못 고치면 덮어쓰지 말고 멈춰서 보고한다.
- **같은 판정을 두 곳에 다른 정의로 넣는다.** "이미 허용된 화면 제외"를 SQL과 Java에 각각 다른 같음 기준으로 넣었다. → 새 필터는 기존 판정 하나만 재사용한다. 두 번째 구현이 필요해 보이면 이유를 보고서에 적는다.
- **생성물을 "생성기 없음"으로 분류한다.** 생산자 테스트(`-D…regenerate…`)가 있는 픽스처를 손으로 고친 원문이라고 보고했다. → 픽스처를 분류하기 전에 그 파일을 쓰는 테스트·속성을 검색한다.
- **지운 뒤 남은 것을 치우지 않는다.** 호출부를 지우면서 그 호출부만 쓰던 enum 상수와 메시지 키를 남겼다. → 무언가를 지운 커밋에서는 지운 식별자를 검색하고, 사용처가 0건이 된 상수·키·테스트를 같은 커밋에서 지운다.
- **같은 값을 보여 주는 경로 중 한 곳만 바꾼다.** 상태 이름의 출처를 상세 조회에서만 바꿔, 같은 상태가 한 답변 안에서 두 가지 이름으로 나왔다. → 표시 문구의 출처를 바꿀 때는 같은 값을 표시하는 모든 경로(상세·이력·목록)를 찾아 함께 바꾸거나, 남긴 경로를 보고서에 적는다.
- **블록을 다시 쓰면서 기존 조건 하나를 조용히 뺀다.** 병합 표의 번호·출처 판정을 새 함수로 옮기면서 "(원본, 번호) 쌍이 모두 서로 달라야 원래 번호를 유지한다"는 옛 조건을 빠뜨렸고, 새 시험도 겹치는 번호를 그대로 기대하도록 썼다(검토자가 발견). → 판정 블록을 옮기거나 다시 쓸 때는 옛 식을 줄 단위로 대조해 조건마다 대응을 확인하고, 빠진 조건은 그 조건이 없으면 실패하는 시험을 둔다. 새 시험의 기대값이 옛 동작과 다르면 이유를 보고서에 적는다.

## 주석

- 기본은 불필요한 새 주석을 쓰지 않는다. 코드 자체로 알 수 있는 내용, 수정 서사·자기 정당화·변경 이유, 삭제된 코드의 흔적은 주석으로 남기지 않는다.
- 현재 코드만 읽어서는 알 수 없는 관측 실패, upstream issue, 필수 순서, 비자명한 단위·형식·인코딩만 새 주석으로 허용한다.
- 기존 주석 중 현재 코드에 유효한 위 근거는 보존한다. 주석 hook은 이를 환기하는 자문이며 의미 판단이나 강제 삭제를 수행하지 않는다.
